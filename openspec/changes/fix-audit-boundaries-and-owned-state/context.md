# Audit boundaries and owned state

This single assigned candidate integrates the eleven source-audit findings and r11 supplier sections 3, 6, 7, 9, 10 and 13 on maintained commit `1f2f58b78ab5901ba820f5e6d66ecd7b1fdeb7e4`. The original audit used divergent `b8512db1`; applicability was rechecked against maintenance. The historical Low soft-affinity severity dissent and unsigned revised ranking remain attributed audit evidence, not independent acceptance of these bytes.

The implementation preserves forwarded-client behavior while using the separately captured socket peer for dashboard trust. Shared HTTP/internal WebSocket header preparation removes only the two local authentication cookies. The public responses/Live WebSocket builder already removed all cookies and retains that policy. Keyless origin admission is performed after authentication and before WebSocket acceptance; it does not alter validated API-key client access. A bearer string ignored by disabled global key authentication remains keyless.

Hard-owner publication uses the repository's existing insert-if-absent primitive. Contenders release provisional leases and rerun selection against the winner, retaining model and caller scope. Soft freshness is a conditional update, distinct from intentional rebinding. Runtime synchronization compares the selection's observed version; its own lease does not create a false version conflict.

Once first hard ownership is published, a later local admission or probe failure does not erase it: another contender may already have observed that winner. Provisional leases still settle, and subsequent requests recheck the retained owner's availability. This deliberately preserves ownership over opportunistic reassignment after a failed first attempt.

The new account hold is a separate boolean because authentication warnings and manual routing preferences belong to different owners. For example, a `reauth_required` account with usable access can remain visibly in that state while `routingHeld=true` blocks routing and explicit usage refresh collects a secondary-window receipt. `PUT /api/accounts/{id}/routing-hold` requires `held` plus `expected: {status, routingPolicy, routingHeld}`. The same optional `expected` tuple is accepted by routing-policy, pause and reactivate requests. Legacy requests without it retain their semantics; consumers needing ownership protection must send the tuple.

`POST /api/accounts/{id}/usage-refresh` accepts `window`, optional `expectedResetAt` and `expected`. Its response separates `fetchSucceeded` from `refreshed`. Only the requested window persisted by that operation, at the expected reset when one is supplied, supplies `usageId`, `recordedAt`, `resetAt` and `usedPercent`; cached data, another window, an empty response or a failed refresh cannot manufacture that receipt. A concurrent caller-owned state change is reported as conflict instead of being restored. This endpoint does not issue a model probe or release the hold.

Dashboard reset consume accepts `expectedCreditId` and `expectedCreditExpiresAt`, constrains the fresh first selection and checks the authoritative durable pin again before consume. SQLite renewal failure or expiry cancels the owning body, with a final ownership assertion before both dashboard and v1 consume admission. An external request already sent when ownership is lost has an unknown outcome. Its durable request pin is retained for reconciliation; source tests establish no external at-most-once guarantee or production double-charge result. The audit's supported controlled lease-loss case is in one process; historical specification scenarios about separate processes are not new runtime evidence here.

Exact cleanup uses `GET /api/sticky-sessions?accountId=...` and `POST /api/sticky-sessions/delete-snapshot` with the selected entries' `key`, `kind`, `accountId` and `ownershipGeneration`. Display names never select the account. A different owner, same-owner delete/recreate, or newly created pin survives the old snapshot. Legacy broad delete APIs remain available and do not provide this contract. Consumers requiring snapshot custody must use the new endpoint.

The additive migration descends from the maintained lifecycle/priority merge. Existing accounts start unheld; existing sticky rows receive unique generations. Legacy bootstrap and revision-remap replays add, and backfill, only a column that is still missing. New ownership writes rotate generations. The generation column is nullable for old-writer compatibility; a row without a generation cannot be submitted to snapshot cleanup. This protocol requires writers that maintain generations. Mixed old binaries that rewrite an existing generated row are outside the snapshot guarantee. Downgrade removes the new hold/generation columns, so preserve or reapply holds before any operator rollback; old binaries cannot enforce a new hold. No automatic downgrade, installation or live replacement is performed by this candidate.

Qualification uses only private test storage, ASGI traffic, fake upstreams and private SQLite. Source checks, independent final review, CI, merge, installation and live behavior are separate facts. Setup B owns publication and final checks; the outside operator alone owns replacement with Codex closed. This context grants no reserve-spending or live account-operation authority.

Final-review corrections fence overlapping availability refresh publication by the last successfully published generation. A completed hold's observation survives older-read completion and ordinary reauthentication clearing even while a later refresh remains pending or fails; reset invalidates all earlier reads. SQLite lease renewal obtains the exact-holder write lock without extending the deadline, checks UTC expiry after that await, and rolls back an extension whose awaited write crosses the old deadline. Tests cover the actual hold endpoint and bridge helper, both consume surfaces, and the microsecond boundary on real private SQLite. PostgreSQL endpoint serialization remains the existing advisory lock. These corrections do not change unknown-consume custody or establish installed behavior.

The later B1 guard-assumptions overlap identifies a separate High direct-WebSocket admission gap: an ordinary new frame could reuse an already-open socket after a successful pause or hold. The final send boundary now consults the routing-unavailable cache after admission waits, refuses the unsent frame through existing cleanup, and preserves its account-owned anchors and retained socket. Private ASGI tests cover pause/hold both before the next frame and during account admission, an eligible control and explicit release followed by reuse. This source correction provides no live reserve-protection, propagation, spending, installation or conversation-migration claim; the operator-owned guard and other report assumptions remain separate.

The later five-capability extension reconciles the operator's fuel-guard capability list against this candidate. Holds for routable `reauth_required` accounts and caller-expected routing writes were already implemented above; they are mapped with protective mutations rather than reimplemented. Usage refresh may now omit `expectedResetAt`: its receipt then names what this poll persisted for the requested window, including that row's reset timestamp and used percent, so a paused `preserve` account can prove a refill whose next reset the caller does not yet know. Dashboard consume with an expected credit or expiry no longer stops at a stale or absent local snapshot; the authoritative fetch decides and still refuses a missing target. `POST /api/accounts/{id}/rate-limit-reset-credits/refresh` is the explicit fresh read: success carries `fetchedAt` from this request's fetch, failure is an error, the cache is untouched, and deletion or a changed upstream identity during the fetch refuses the observation. The untargeted usage-reset consume, whose upstream request names no credit, refuses caller expectations instead of silently dropping them. For example, after a weekly refill the operator polls `usage-refresh` with `window: secondary` and the expected `{paused, preserve, held}` tuple; the response returns the new `resetAt`, `usedPercent` and persisted `usageId` while the account stays unservable. Serialization, the final account/claim observation and the exact credit ID sent upstream do not prove upstream consume atomicity. These are private SQLite/ASGI source results, not installed or live behavior.
